## 题目

基于执行反馈的 LLM 辅助移动机器人任务规划

---

## 摘要（约 150–250 字）

本文实现了一个由LLM所驱动的任务规划系统并再次基础上进行仿真测试。系统将自然语言请求转换为经过验证的高层技能调用。LLM 根据自然语言从固定白名单中选择技能，验证器在执行前检查每个调用，执行后系统读取返回的结果，可以在超时、障碍等失败场景下进行有限的恢复，包括将执行反馈发送给 LLM 进行重规划。在仿真实验中，系统能可靠完成单点、多航点导航，安全拒绝非法与未知技能，并使用障碍/窄缝检测机制来减少碰撞和卡死。

---

## 1. 任务定义与设计目标

### 1.1 任务

我们的目标是：可以通过自然语言指令，如“Go storage, then workbench, and stop”（此处“Storage”、“Workbench”等地点为提前在房间内指定的位置），驱动Agent完成对应的任务。为了保证安全性和可控性，我们不希望LLM能够直接控制机器人，其行为方式应该只能通过调用预设的技能，并且其任何行为都必须经过安全确认。此外，我们希望所有的行为都可以得到反馈，并且希望通过反馈来更好地完成任务。
### 1.2 设计原理

由此，我们很自然的想到，LLM的部分仅负责理解自然语言，将用户的指令转换为一个可控的行为序列。在这个过程中，可以使用一个专门的验证器来保证LLM给出的指令是合法的。此外，执行过程中每个技能都返回一个结构化结果，使得整个系统根据该结果进行有界恢复（例如倒车并重新寻路），并在必要时使用LLM 进行重新规划。通过这种方式，系统既能利用大模型对自然语言的理解能力，又能减少LLM直接控制机器人带来的问题。

### 1.3 好处
- 自然交互性：可直接使用自然语言进行交互，对用户隐藏底层细节。
- 可靠性：技能机制和参数清晰、返回值高度结构化；
- 安全性：采用白名单和验证器机制，仅允许LLM调用预设好的技能，仅允许LLM在规定的区域运动。采用有界恢复原则，在操作失败或者系统失控的时候，及时防止系统继续进行危险操作或者违规操作。
- 可复现性：使用的所有环境、模型、算法都是基于公开的，且配备有完整的操作文档。

## 2. 系统架构与技能接口设计

### 2.1 架构

```text
自然语言请求
      ↓
Planner（模拟规划器/LLM规划器）
      ↓ raw plan
Validator（白名单、Schema、是否在空间范围内、执行步数上限）
      ↓ validated calls
Skill Executor
      ↓
RobotSkills → /agent0/cmd_vel → Webots
      ↓
SkillResult
      ↓
RecoveryManager（retry / backup / replan / stop）
      ↓
ExecutionFeedback → Planner
```

### 2.2 技能接口

| 技能 | 参数 | 成功条件 | 超时 | 返回 |
|---|---|---|---|---|
| navigate_to | x,y,theta | 位置误差≤0.10m，航向误差≤0.15rad | 30s | success/reason/elapsed_time_s/error |
| follow_waypoints | waypoints[] | 所有航点到达 | 30s/航点 | last_reached_index |
| stop | 无 | 零速度发布 | 2s | success/reason/elapsed_time_s |

## 3. 实现细节

### 3.1 导航

- 底盘：全向轮 RoboMaster；
- 航向转换：yaw = normalize(-radians(bearing))；
- 控制器：分别对x、y、theta 三组 参数进行PID控制；
- 地图：使用Webots Supervisor 导出物体真实位置/尺寸，生成占据栅格图（这一步可以使用SLAM方法代替，但是在模拟环境中效果并不好，因此使用了别的方法代替）；
- A*：我们采用A*作为基础的寻路算法。但是我们发现由于地图精确度不高，小车在最短路径上面的运动容易贴墙走并且剐蹭到障碍物，因此我们将小车距离最近障碍物的距离加入到了A*算法的代价函数中，来避免上述情况。此外，有时候小车会倾向于钻桌角和柱子的缝隙，然后由于自身宽度而卡在中间，为此我们设定如果某个格子距离障碍物的距离太过接近，则是不可通行的。以此来实现安全居中的路径规划。
- 此外，我们加入了窄缝检测机制。如果小车的车载Scaner认为，前进方向可通行缝隙宽度小于0.3m，此时将触发停车并重新规划路线。
- 为了防止在通道地形中反复撞墙，我们设定了墙排斥机制，即左右间隙小于 0.30m 时横向纠偏并减速。

### 3.2 LLM 工具调用

- 我们使用了来自中转站的API，调用GPT5.5（自称）来进行实验。在系统中，LLM只能看到来自系统的提示词、预先设定的几个地点的坐标、房间的空间边界（坐标边界），预设的三个技能的详细定义，以及使用者发来的自然语言要求。模型的接入上，使用了OpenAI的兼容接口，可供他人自行配置。如果说没有配置Key或者说API请求失败时，则会激活使用结构化语言的模拟规划器。

### 3.3 验证器

六层验证：
验证器负责对LLM指令进行合法性验证，主要包括以下几个方面：
1. 计划长度，限制每个任务能够使用的最多技能数，防止生成过长且不可控的计划；
2. 固定白名单，检查使用的技能是否在技能列表中，不允许未知技能；
3. JSON Schema，检查技能的参数是否符合要求，如参数类型、范围等；
4. 工作空间，检查目标坐标是否处于工作空间之内；
5. 前置条件，检查机器人是否存在、可用，以便执行任务；
6. 重试/重规划限制，不允许过多重试次数和重新计划次数，以保证重规划或重试是有界的。

### 3.4 执行反馈与有界恢复

- 每个技能都会返回 `SkillResult`；
- 如果执行失败则会根据情况触发恢复动作，retry / backup_and_retry / replan / stop_and_report；
- `ExecutionFeedback` 只包含任务级信息，不包含原始传感器数据；
- `--max-retries`、`--max-replans` 控制有界性。

## 6. 局限性、安全考虑与下一步

### 6.1 局限

- WSLg 渲染性能有限；
- 无 `/agent0/odom`，用 GPS + compass；
- 参考控制器轮半径常量有误；
- Supervisor 地图仍需要默认尺寸近似个别物体。

### 6.3 下一步

- 使用 slam_toolbox 融合激光与几何地图；
- 动态障碍规避；
- Docker 一键复现；
- 更多失败场景的 LLM 重规划实验。
